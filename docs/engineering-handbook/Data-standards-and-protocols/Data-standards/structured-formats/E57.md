# E57

E57 is a vendor‑neutral, open format for LiDAR and 3D scanning point clouds.
It is commonly used in conservation, archaeology, and architectural documentation, and supports storage of large point sets together with acquisition metadata.

This page provides practical, non‑normative guidance for handling E57 within CH Cloud workflows.

## What E57 is good for

Use E57 when you need:

- high‑fidelity capture of raw or near‑raw scanning outputs (measurement‑grade point clouds)
- long‑term interchange between tools and institutions using different scanning ecosystems
- baseline ingestion of 3D scan datasets where preserving precision matters

## When E57 is not a good fit

E57 is usually not ideal when:

- you need web‑first visualisation (E57 often requires conversion and downsampling for interactive viewers)
- you need compact distribution for end users (derived formats are more suitable)
- the workflow is primarily mesh‑based rather than point‑cloud‑based (publish mesh derivatives alongside E57 where needed)

## Interoperability considerations

### 1) Capture metadata must be preserved

To avoid losing interpretability, publish at least:

- device and acquisition context (scanner and camera metadata)
- coordinate reference system and units, or an explicit statement if unknown
- registration and alignment method, if multiple scans were merged
- scale and origin conventions used in downstream conversions

### 2) Derived outputs are expected

Many workflows require derived representations:

- downsampled point clouds for preview
- meshes for rendering
- normalised coordinate frames
- metadata sidecars for viewers and portals

Document:

- which derived artefacts exist
- how they were produced (tooling and parameters)
- how they relate to the original E57 (provenance)

### 3) Storage and transfer

Point clouds can be large.
Plan for:

- predictable packaging (single archive, multi‑file sets, manifests)
- checksum publication for integrity
- stable naming and versioning for repeat exports

## Validation and quality checks

- file integrity checks (readability in standard libraries and tools)
- presence of CRS and units metadata, or explicit “unknown”
- bounding box and point count sanity checks
- optional density and outlier diagnostics for ingestion pipelines
